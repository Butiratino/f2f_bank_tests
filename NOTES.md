# Заметки по тестам

## Наблюдаемоые баги в поведении приложения

- Критический; TC-API-TRANSFER-015 - API перевода принимает номер телефона и назначение платежа, но они не сохраняются в базе данных и не возвращаются в истории транзакций.

- Критический; TC-API-REG-002 - API регистрации принимает роль admin, переданную со стороны клиента.

- Критический; При регистрации пользователя номер телефона не запрашивается и не привязывается к аккаунту, из-за чего логика перевода "по номеру телефона" не имеет полного бизнес-сценария.

- Высокий; TC-BAL-009 - После очистки сессии и повторного входа в шапке отображается баланс 0 до ручной перезагрузки страницы.

- Высокий; TC-AUTH-006, TC-REG-002 - При клике на публичный логотип со страниц авторизации и регистрации отправляется запрос защищенного эндпоинта баланса для незалогиненного пользователя.

- Высокий - Вкладка Main (корневой роут) фактически реализует функционал переводов, что скрывает бизнес-логику в интерфейсе.

- Высокий; TC-API-REG-015, TC-API-REG-016, TC-API-REG-017 - API возвращает системную ошибку 500 вместо 422 при передаче значений, превышающих лимит длины для email, имени и фамилии.

- Высокий; TC-API-REG-003, TC-API-REG-004, TC-API-REG-006, TC-API-REG-012 - API возвращает некорректный статус 400 вместо 422 для невалидных форматов email (без доменной зоны, с двумя @, кириллицей или состоящих из пробелов).

- Высокий; TC-API-REG-005, TC-API-REG-008, TC-API-REG-009 - API принимает email короче 6 символов, а также пароль короче 8 символов и длиннее 64 символов.

- Высокий; TC-API-REG-010, TC-API-REG-011, TC-REG-011 - API и форма регистрации принимают пустое имя, а также имя и фамилию, состоящие исключительно из пробелов.

- Высокий; TC-API-REG-007, TC-REG-010 - API и форма регистрации принимают кириллический пароль.

- Высокий; TC-REG-013, TC-AUTH-017 - Формы регистрации и входа принимают пароль, состоящий из пробелов.

- Высокий; TC-API-AUTH-005, TC-AUTH-009 - При попытке авторизации API принимает кириллический email и email без доменной зоны.

- Высокий; TC-API-AUTH-006, TC-AUTH-010 - При авторизации с кириллическим паролем API возвращает статус 401 вместо 422.

- Высокий; TC-AUTH-011, TC-REG-007 - Формы входа и регистрации не задают HTML-атрибуты pattern, minlength и maxlength для полей ввода.

- Высокий; TC-AUTH-012, TC-AUTH-013, TC-AUTH-014, TC-AUTH-015 - Форма входа пропускает слишком короткие и слишком длинные значения email и пароля до этапа запроса к API.

- Высокий; TC-API-TRANSFER-005, TC-TRANSFER-006 - API и форма перевода принимают номер телефона с буквами (API очищает нецифровые символы вместо возврата ошибки валидации).

- Высокий; TC-API-TRANSFER-010, TC-API-TRANSFER-011, TC-TRANSFER-009 - API и форма перевода принимают пустое назначение платежа, а также назначение длиннее лимита в 256 символов.

- Высокий; TC-API-BAL-007, TC-API-TRANSFER-014, TC-BAL-007, TC-TRANSFER-016 - API и формы пополнения баланса и перевода принимают денежные суммы с тремя знаками после запятой.

- Средний; TC-BAL-002, TC-TRANSFER-001 - В таблице транзакций заголовки Operation Type и Operation Status перепутаны местами относительно выводимых данных (сначала отображается статус, затем тип).

- Средний - В темной теме браузера Chromium текст на светлом фоне таблицы транзакций имеет недостаточный контраст и нечитаем.




## Бизнес-правила

Это согласованные правила для входа и регистрации. Они хранятся в тестовых данных `helpers/testData.ts` и проверяются на уровнях UI и API.

| Поле | Правило | Обоснование |
| --- | --- | --- |
| Email | Только латинские символы | Бизнес-правило проекта |
| Email | Формат `local@domain.zone` | Проект требует доменную зону |
| Email | Минимум 6 символов | Короткий практический вариант: `a@b.co` |
| Email | Максимум 50 символов | `UserOrm.email` использует `String(50)` |
| Пароль | Только латинские/ASCII-символы | Мировой стандарт |
| Пароль | Минимум 8 символов | Распространённый минимальный порог для паролей |
| Пароль | Максимум 64 символа | Максимальный порог |
| Имя | От 1 до 50 символов | В БД используется `String(50)` |
| Фамилия | От 1 до 256 символов | В БД используется `String(256)` |
| Телефон перевода | Только `+` и 10–15 цифр, без букв и других символов | Формат номера для перевода |
| Назначение платежа | Обязательное поле, от 1 до 256 символов | Бизнес-правило перевода |
| Сумма перевода | Положительное значение, минимум `0.01`, не более 2 знаков после запятой | Денежное значение с точностью до копейки; верхний лимит не задан |

## Теги

- Категории: `@main`, `@transaction`, `@profile`.
- Доменные теги: `@auth`, `@registration`, `@balance`, `@transfer`.
- Теги критичности: только lowercase `@critical`, `@high`, `@medium`, `@low`.
- Критичность: `@critical` означает потерю денег/данных, обход авторизации или основной happy path; `@high` означает основной рабочий сценарий, security boundary или существенную бизнес-валидацию; `@medium` означает отдельное ограничение или негативный boundary-кейс; `@low` означает второстепенную навигацию и UI-поведение.
- Теги назначения: `@smoke`, `@negative`, `@validation`, `@api`.
- Тег состояния: `@need2fix` означает подтверждённый дефект приложения, оформленный через `test.fail`.
- Каждый тест имеет комментарий с идентификатором `TC-*`, доменной зоной и критичностью.
- Кириллический email, кириллический пароль и email без доменной зоны проверяются на API-уровне как бизнес-правила. UI-suite дополнительно проверяет пользовательский результат submit: такие значения не должны успешно авторизовать или регистрировать пользователя; это не заменяет API-проверку.

## Текущие приоритеты тестов

- **Критический:** успешная регистрация, успешная авторизация, пополнение баланса, выполнение перевода, уязвимости ролевой модели, доступ к защищенным маршрутам без токена или после логаута, потеря данных транзакций.
- **Высокий:** неверные учётные данные показывают ошибку и оставляют пользователя на странице входа, перевод при недостаточном балансе, отсутствие обязательных полей, невалидные форматы (email, телефон, суммы), 500-е ошибки сервера вместо 422.
- **Средний:** граничные лимиты текстовых полей, специфичная валидация (пробелы, два @, кириллица), ошибки UI-состояния (рассинхрон баланса), утечка неавторизованных запросов.
- **Низкий:** открытие модальных окон без действий, UI-переходы по ссылкам, визуальные дефекты, доступность элементов.

## Управление ожидаемыми падениями

Подтверждённые дефекты приложения помечены тегом `@need2fix` и аннотацией
`test.fixme(true, reason)`.

Запуск только известных дефектов:

```bash
npm run test:need2fix
```


На текущем состоянии приложения полный прогон содержит 42 ожидаемых дефекта,
помеченных `@need2fix`; непомеченное падение считается ошибкой тестов или новым
дефектом и требует отдельного разбора.
